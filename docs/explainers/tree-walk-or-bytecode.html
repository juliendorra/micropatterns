MicroPatterns · firmware architecture note

Tree Walk or Bytecode

How a script becomes pixels on both devices today, what a mini VM would actually change, and why — measured across twelve real scripts — the structure worth attacking is the parsed program, not the display list.

More effective? Yes — but you already built half of it

The epoch-tagged slot caches in micropatterns_command.h are parse-time compiler work, done lazily at runtime.

Fixes the Watchy memory class? The half that has actually failed

Capacity is fine today. Fragmentation from the parse is what crashed the watch — and that is the parse tree's fault.

Faster or slower? Faster — but not where I guessed

Generation is only 3–15% of a render on the real scripts. Parsing is 14–57%. The CPU win is in not parsing at all.

Stage 01 — 03

What happens today

A render is three passes over three different representations. This is true on both devices: Watchy_MicroPatterns/src/main.cpp builds the parser, runtime, rasterizer and occlusion buffer straight out of the M5Paper tree — no copies, one codebase, selected by a compile-time canvas typedef in mp_canvas.h. Only the last two boundaries are timed; parse time is invisible on both.

The Watchy runs the same three passes — today, in shipped firmware

This is worth stating plainly because the design doc predicted otherwise. watchy-port-design.md §7.3 concluded that the display-list path was over budget by roughly 7× on a no-PSRAM PICO-D4 and recommended a streaming renderer that never materializes a list at all. The streaming renderer was never built. The naive port fit on the first try, because two changes landed underneath that analysis and invalidated its arithmetic: DisplayListItem became a 40-byte POD, and the occupancy map went to one bit per pixel.

What differs on the watch is constants and consequences, not structure.

The failure that has actually happened

From the comment above the guard in micropatterns_drawing.cpp:131: parsing the largest script fragmented the Watchy's heap down to a ~26 KB largest free block. The occupancy map's allocation could not be satisfied, and because exceptions are disabled on Arduino, std::vector::resize called abort() outright — the watch rebooted mid-render, every time that script was selected.

Note what that is and is not. It is not running out of memory: there was plenty of free heap in total. It is the parse tree's thousands of small String and tree-node allocations shredding the heap into pieces too small to hold a 5 KB contiguous block. The shipped fix checks heap_caps_get_largest_free_block() and degrades. It makes the crash into a wrong picture — it does not stop the fragmentation.

The hot path

One rectangle, forty times

Everything about the speed question lives inside one loop body. Take the simplest interesting script:

VAR $c = 0
REPEAT COUNT=40
  RECT X=$c Y=10 WIDTH=8 HEIGHT=8   ← this line runs 40 times
  LET $c = $c + 5
ENDREPEAT

The RECT is executed forty times, and each execution costs whatever the representation makes it cost. That is the whole argument, and it is visible in two files: the body is a std::list walked per iteration, and each parameter goes through findParam, which is a linear scan over a red-black tree of Arduino String keys.

The change

What a VM actually replaces

A mini VM is not a new render pipeline. It swaps out one representation — the parsed program — and leaves the display list, the rasterizer and the panel driver exactly as they are.

The memory question

Two different failures, two different fixes

The Watchy has two distinct memory problems, and conflating them is what makes this question hard to answer.

Capacity is about totals, and it scales with primitives drawn: the parsed program is fixed by the length of the script, but the display list is proportional to what the script emits, and a REPEAT COUNT=40 multiplies that by forty without adding a line. Bytecode moves the starting point of that line down. Only deleting the display list changes its gradient.

Fragmentation is about shape, does not scale with anything, and is the one that has actually crashed the device. It comes almost entirely from the parse — which is the representation bytecode replaces outright.

Capacity is not currently binding. Fragmentation is.

Corrected in the design doc

The naive-port table in watchy-port-design.md §7.3 charged 480 KB to per-item std::map nodes and 40 KB to a one-byte-per-pixel occupancy map. Both are gone: the item is a 40-byte POD, the map is 1bpp. The 861 KB total is really about 170 KB, the "does not fit" verdict was wrong, and the streaming renderer it recommended was never needed. That section now carries a dated correction saying so, and reweights the bytecode item from "defer until measured" — because it has since been measured, by a crash.

And a correction to my own speed claim

Display-list generation is 3–16% of host render time on the real scripts — not the dominant phase I expected. city.mp, at 72%, is the outlier that made it look otherwise. So a VM's benefit to interpretation speed on the real corpus is small.

What is large is parsing: 14% to 57% of render time at 200 × 200, and the single biggest phase on City 2. That reframes the third step. Serializing bytecode so the watch never parses stops being a nice-to-have at the end of the list and becomes the largest CPU saving on the table — worth more than making the interpreter faster, on every script the device actually runs.

A live incident

Why Seascape II flashes and shows its title on a button re-run

Reported behaviour: pressing the bottom-left button to re-run Seascape II always produces a panel flash and the script's title frame, "as if it was struggling to render it", while the 77-second timed re-run displays directly. The two paths call the same function with the same arguments — showScript(g_currentScript, false), no title — so the title cannot be coming from the re-run itself.

It is coming from a reboot. Boot forces a full refresh (g_updatesSinceFull starts at the de-ghost interval, so the first beginPanelUpdate() is a full flash) and then calls showScript(g_currentScript, true) — the only path that announces a title for an unchanged script. Flash plus title is the boot signature, not a render signature.

What makes the button path reboot and the timer path not is one line the timer never executes: MPProvisioning::openWindow(). Every button press opens the BLE provisioning window, and that builds the BLE stack — about 90 KB of internal DRAM by the firmware's own accounting — before the release edge starts the render.

How to confirm in one press

Leave the serial console attached and press bottom-left. A render prints logHeap "after parse" and carries on. A reboot prints the boot banner and MPCON|ready again. Nothing else distinguishes the two from the panel, which is exactly why it looked like a slow render.

The estimate for the parse tree is derived (command count × the per-command struct plus map nodes), not measured, and the BLE figure is the firmware's own comment; the MPCON|alive … heap= heartbeat before and after a press gives the real number.

What it says about the two designs

This is the third time the parse tree has been the structure that breaks on the watch, and the first time it has done so without any help from the display list — Seascape II's peak list is 11,600 bytes. Three fixes exist at three depths: stop opening the BLE window on the re-run button (it is only needed for the sync gesture), which cures the symptom; flatten the command stream, which shrinks the tree by an order of magnitude; or ship bytecode, which removes the parse from the watch entirely. Streaming rendering would not have changed this outcome at all.

Orthogonality

The two decisions are independent

It is easy to read "mini VM" and "streaming renderer" as competing answers to the same question. They are not. One changes the front half, the other changes the back half, and any of the four combinations builds. Both devices sit in the same quadrant today — top left.

Sequencing

What order to do it in

This is the part I had backwards before checking what the Watchy actually runs. With the naive port shipped and fitting, streaming is no longer the thing standing between you and a working watch — it is a headroom investment for scripts that do not exist yet. The front half moves up.

  1. Flatten the command stream, intern the parameters. Replace the nested std::lists with a vector plus jump offsets, and replace map<String, ParamValue> with an enum-indexed fixed array. This is about 80% of the VM's value, it is a mechanical and testable change to the parser's output stage, and it targets the fragmentation that is already causing a visible bug. The golden-image harness in tools/host_harness/golden/ is the regression net — and "does the occupancy map still allocate on the largest script" is a one-line pass/fail on top of it.
  2. Full bytecode and serialization. Promoted, on the measurements. Parsing is the largest phase of a render on City 2 at the Watchy's canvas — 57% — and it is pure overhead the device does not have to do at all: compile in the emulator or the server, ship the bytes, never parse on the watch. That also removes the fragmentation source at its root rather than shrinking it. The costs are real — a dispatch loop, a wire format, and a third implementation to keep pixel-identical with the JS emulator — but the payoff is now the biggest single CPU saving identified anywhere in the render path.
  3. Streaming renderer — when a script needs it, not before. Still the only thing that flattens the capacity line, and still worth building eventually. But it costs the occlusion culling and the reverse-order paint, and the device it was designed to rescue is already running without it. Let a real script cross the line first.

Before any of it: read the logs you already have

Both firmwares log the generation-versus-rasterization split on every render, and the Watchy additionally calls logHeap() after parse, after display list, and after render. Between them those answer both open questions without a line of new code: what fraction of a render the front half actually is, and how far the largest free block falls during a parse. On nested-REPEAT scripts like city.mp I would expect generation to dominate; on sparse scripts, not. That is a log-mining exercise, not a rewrite.

One thing not to conflate

The git history already settled a compiler-versus-display-list question, and the display list won. That was about the render pipeline. A VM is about the representation of the command stream and sits underneath either pipeline. It is not the losing path coming back.

Implemented · 2026-09-03

What happened when it was built

Steps 1 and 2 above shipped together as mp_program.h: the parser compiles each line straight into a flat program (48-byte instructions, an 8-byte operand pool in postfix, interned slots, indexed assets), the runtime is a small VM over it, and both firmwares compile once at the end of a sync — after WiFi is down — and store the bytes next to the source. A render streams the stored program into RAM and never parses. Output was held byte-identical to the tree walker on the 18 goldens, on the serialize→deserialize path, and on the 576-render oracle used for the tables above.
